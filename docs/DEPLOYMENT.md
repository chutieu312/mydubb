# Deployment: online mock Private Beta (Milestone 2B)

Target: `https://mydubb.com` running the production Docker image on free tiers. Audio
processing is **mock** (pass-through); translation is real (Azure Translator, Milestone 3A) and
speech is real (Azure Speech, Milestone 3B), see "Current deployment", "Azure Translator" and
"Azure Speech" below.

```
Browser ──HTTPS──► Render edge (TLS, mydubb.com) ──► Render Free web service "mydubb"
                                                     (Oregon, Docker image, 1 instance)
                                                          │
                                                          ▼
                                                   Neon Free PostgreSQL
                                                   (AWS US West 2, Oregon)
```

Neither Render nor Neon offers a California region; Oregon (US West) is the closest for both,
and keeping them in the same region minimizes database latency.

Configuration lives in [`render.yaml`](../render.yaml) (Render Blueprint). Secrets are never
stored in the repository or sent in chat:

| Variable | Source |
|---|---|
| `DATABASE_URL` | Neon direct connection string, pasted into Render once |
| `ACCESS_CODE` | Generated by Render (random 256-bit value); read it in the Render dashboard |
| Everything else | Fixed values in `render.yaml` |

## Free-tier behavior to expect

- **Render Free** web service: spins down after 15 minutes without traffic; the next visit
  waits for a cold start (often around a minute). 750 free instance hours per workspace per
  month. The filesystem is ephemeral: generated results disappear on restart, deploy or
  spin-down, and the app then reports "result expired".
- **Neon Free**: the database compute suspends when idle and wakes on the next connection
  (adds a short delay to the first request).
- If Render or Neon ever asks for a payment method or a plan upgrade during these steps, stop
  and check with the team; this setup must stay on free plans.

## One-time setup

### 1. Neon database

1. Sign in at https://console.neon.tech (signing in with GitHub is fine).
2. Create a project:
   - Project name: `mydubb`
   - Postgres version: **17** (same as CI)
   - Cloud provider: **AWS**, region: **US West 2 (Oregon)**
3. Open the project dashboard and click **Connect**. In the connection dialog:
   - Branch: `main` (or `production`, whichever is the default), database: the default
     (`neondb`), role: the default owner role.
   - Turn **Connection pooling OFF** so the hostname does **not** contain `-pooler`. Migrations
     run at startup and need a direct connection.

     `postgresql://<role>:<password>@ep-<name>.us-west-2.aws.neon.tech/neondb?sslmode=require...`
4. Keep it only in your clipboard or password manager for the next step. Do not commit it or
   paste it into chat. The app normalizes `postgresql://` URLs itself; paste it unchanged.

### 2. Render Blueprint

1. Sign in at https://dashboard.render.com.
2. Click **New** → **Blueprint**.
3. Connect GitHub if Render asks:
   - Choose **GitHub**, authorize Render, and install the **Render** GitHub App.
   - On the installation page choose **Only select repositories** → `chutieu312/mydubb`
     → **Install**. (Render then sees only this repository.)
4. Back in Render, select the `chutieu312/mydubb` repository.
5. Blueprint name: `mydubb`; branch: `main`. Render reads `render.yaml` and lists one web
   service named `mydubb` on the **Free** plan in **Oregon**. Check both before continuing.
6. Render asks for the value of `DATABASE_URL`: paste the Neon connection string from step 1.
   `ACCESS_CODE` is generated automatically.
7. Click the button that creates the resources (for example **Deploy Blueprint**).
8. Open the `mydubb` service → **Events**/**Logs** and wait for the first deploy (the Docker
   build takes several minutes). A healthy start logs, in order:
   - `Running upgrade  -> 0001` and `Running upgrade 0001 -> 0002` (database migrations),
   - `Running in production with MOCK providers ...` (expected warning),
   - `Application startup complete.`
9. The service page shows its Render URL, e.g. `https://mydubb.onrender.com` (Render may add a

10. Get the Access Code: service → **Environment** → `ACCESS_CODE` → reveal and copy. Store it in

### 3. Custom domain (GoDaddy DNS)

`render.yaml` declares `mydubb.com`, but in practice the Blueprint did **not** attach it when
the service was created, so add it in the dashboard. Render then adds `www.mydubb.com`
automatically and redirects it to `mydubb.com`.

1. In Render: service → **Settings** → **Custom Domains** → **Add Custom Domain** →
   `mydubb.com` → save (skip if it is already listed). Render shows the DNS records it
   expects: a `CNAME` for `www` and, for the root, a `CNAME`/`ANAME`/`ALIAS` **or an `A` record
   with `216.24.57.1`**. GoDaddy has no ALIAS for the root, so use the `A` record.
2. In GoDaddy: **My Products** → `mydubb.com` → **DNS**, or open
   `https://dcc.godaddy.com/control/portfolio/mydubb.com/settings?tab=dns` directly. Ignore the
   "Let's connect" wizard (its cards create forwarding/website setups we do not want); use the
   **DNS Records** table:
   - **A** record, name `@`: edit the existing one (shown as "Parked", which stands for
     GoDaddy's parking IPs) or add one, value
     **`216.24.57.1`**, TTL 600 seconds (or "1/2 hour"). Delete any other `A` records for `@`.
   - **CNAME** record, name `www`: edit the existing one (usually pointing to `@`), value
     **`<your-service>.onrender.com`** (the hostname from step 2.9), TTL 600 seconds.
   - Delete every **AAAA** record (Render uses IPv4 only; AAAA records break routing).
   - Under **Forwarding**, make sure no domain or subdomain forwarding is configured.
   - Leave `NS` and `SOA` records unchanged.
3. Check propagation (Windows Command Prompt, PowerShell or Git Bash):
   ```bash
   nslookup mydubb.com        # should answer 216.24.57.1
   nslookup www.mydubb.com    # should show the onrender.com hostname
   ```
   Propagation can take from minutes to a few hours.
4. In Render → **Custom Domains**, click **Verify** for each domain. Render then issues the TLS
   certificates automatically. Wait until both show as verified with certificates issued.

### 4. Online verification

1. Browser: open `https://mydubb.com` (desktop and phone). Check the padlock, the mock banner,
   log in, run one dubbing job, play and download the MP3, log out.
2. `http://mydubb.com` and `https://www.mydubb.com` must end up on `https://mydubb.com`.
3. Smoke test from Git Bash in the repository root (the Access Code is typed without echo and
   never stored):
   ```bash
   read -rs ACCESS_CODE && export ACCESS_CODE      # paste with Shift+Insert, press Enter
   echo ${#ACCESS_CODE}                             # prints only the length (Render: ~44)
   BASE_URL=https://mydubb.com SMOKE_SKIP_WRONG_CODE_CHECK=1 PYTHON=python sh docker/smoke-test.sh
   unset ACCESS_CODE
   ```
   Expected last line: `mock job <id> completed; result and audio retrievable`.
   `SMOKE_SKIP_WRONG_CODE_CHECK=1` avoids spending one of the 5 failed attempts per client per
   15 minutes allowed by the brute-force protection. A `login failed: HTTP 429` means that
   allowance is used up (all users behind the same IP share it): wait 15 minutes. `HTTP 401`
   means the pasted code is wrong or incomplete. In Git Bash, paste with **Shift+Insert** or
   right-click → Paste: **Ctrl+V inserts a control character** instead of pasting. The script
   refuses codes containing whitespace or control characters without sending them.
4. Security headers:
   ```bash
   curl -s -D - -o /dev/null https://mydubb.com/api/health | grep -iE "strict-transport|content-security|x-frame"
   ```
5. Client IP header check: in Render → **Logs**, search for `CLIENT_IP_HEADER`. No match after
   the logins above means the edge header is present and brute-force protection identifies
   clients correctly. If the warning
   `CLIENT_IP_HEADER 'cf-connecting-ip' is configured but absent` appears, report it: the
   per-client limit is then bypassable and needs a different header (the global limit still
   applies).

## Azure Translator (Milestone 3A)

Production uses Azure translation since 2026-10-22 (see "Current deployment"); these are the
steps that were followed. Cost rule: use
only the **Free (F0)** pricing tier; never pick Standard (S1) without a decision.

### 1. Create the resource (Azure portal)

1. Sign in at https://portal.azure.com and open
   https://portal.azure.com/#create/Microsoft.CognitiveServicesTextTranslation (create
   "Translator" - a single-service resource).
2. **Subscription**: your Azure subscription. **Resource group**: create a new one, e.g.
   `mydubb`.
3. **Region**: choose **Global** (Microsoft's default recommendation; then no region setting is
   needed). If you pick a specific region, you must set `AZURE_TRANSLATOR_REGION` later.
4. **Name**: any unique name, e.g. `mydubb-translator`.
5. **Pricing tier**: **Free F0** (one free resource per subscription; 2 million characters per
   month included, 2 million per hour rate cap). On F0 Microsoft rejects requests over the
   free quota (`403001`/`429`) instead of charging; MyDubb shows "quota or rate limit reached".
   If the portal offers only paid tiers, stop and check with the team.
6. **Review + create** → **Create** → **Go to resource**.
7. Left menu → **Resource Management → Keys and Endpoint**. Copy **KEY 1** and note
   **Location/Region**. Do not paste the key in chat, issues, pull requests or logs.

### 2. Live smoke test from your computer

Put the key in `backend/.env` (git-ignored; edit it in your editor):

```
AZURE_TRANSLATOR_KEY=<KEY 1>
AZURE_TRANSLATOR_REGION=<Location/Region, omit for Global>
```

```bash
cd backend
uv run python -m scripts.azure_translator_smoke
```

It sends one short synthetic transcript (about 250 characters), prints the Vietnamese result
and checks that `neural network`, `gradient descent`, `loss function`, `Spring Boot`, `API`,
`JSON`, `pull request`, `CI/CD` and `Dependency Injection` stayed exactly as written. Exit code
0 means the live service, credentials, no-translate markup and parsing work. Unit tests with
fake HTTP do not replace this check. To see the request in the app too, start it with
`TRANSLATION_PROVIDER=azure` (README, "Azure translation + mock audio") and run a job; the
backend log line `Azure Translator request ok: ... metered_chars=N` shows how many characters
Microsoft charged. Measured on 2026-10-22 (F0, Global endpoint, region `westus2`):
`metered_chars` equals `sent_chars`, i.e. the no-translate markup **is billed**. Each protected
term occurrence adds 31 characters to the usage counted against the 2 million characters per
month of F0, so term-dense transcripts use noticeably more quota than their plain length.

### 3. Enable on Render (done for production on 2026-10-22)

Render → service **mydubb** → **Environment** → add `TRANSLATION_PROVIDER=azure`,
`AZURE_TRANSLATOR_KEY` (mark as secret) and, only for a regional resource,
`AZURE_TRANSLATOR_REGION`; keep `PROVIDER_MODE=mock` and
`ALLOW_MOCK_PROVIDERS_IN_PRODUCTION=true` (speech and audio are still mock). Save; Render
redeploys. The site banner then reads "Beta: real translation, mock audio" and the form
shows that the transcript is sent to Azure. `render.yaml` is intentionally unchanged: the key
must be entered in the dashboard, never committed.

To switch back: remove `TRANSLATION_PROVIDER` (or set it to `mock`) and save. If the key is
missing or invalid the service refuses to start (the log names the variable, not its value).

### Expected behavior and limits

- Jobs fail with a clear message on bad credentials, quota/rate limits, timeouts, network
  problems, service errors or an unexpected answer. Nothing is retried automatically and the
  mock is never used as a fallback; the user submits again.
- Code-like symbols in the transcript are not protected: Azure's translation itself may alter
  them (observed live: `a && b` came back as `a & b`; `<`, `>` and single `&` were kept).
  Only the glossary terms are guaranteed.
- Only terms in the glossary are protected; see
  [ARCHITECTURE.md](ARCHITECTURE.md#azure-translator-and-technical-terms-milestone-3a).
- The key is rotated in the Azure portal (Keys and Endpoint → Regenerate) and updated in
  Render; a regenerated key invalidates the old one immediately.

Put the values in `backend/.env` (git-ignored) and have `ffmpeg` and `ffprobe` on `PATH` (or run

AZURE_SPEECH_KEY=<KEY 1>

cd backend

`speech-samples/speech-AndrewMultilingual.mp3`, `speech-EmmaMultilingual.mp3` (and
`speech-multi-chunk-*.mp3`, which uses an 80 character chunk limit, so each line is its own

**Listen to them** and judge: clear Vietnamese, recognizable English terms, no lost or repeated

### 3. Enable on Render (done for production on 2026-10-22)

Render -> service **mydubb** -> **Environment** -> add `SPEECH_PROVIDER=azure`,
`AZURE_SPEECH_KEY` (secret) and `AZURE_SPEECH_REGION`; keep `PROVIDER_MODE=mock` and
`ALLOW_MOCK_PROVIDERS_IN_PRODUCTION=true` (audio processing is still a pass-through). The image
already contains FFmpeg. The banner then reads "Beta: real translation and speech, duration not
adjusted" and the form says that text is sent to Azure Translator and Azure Speech. Remove
`SPEECH_PROVIDER` to go back to the mock fixture. A missing key or region, or a missing FFmpeg,
stops the service at startup; the log names the variable, never its value. `render.yaml` is
unchanged.

### Expected behavior and limits

- Without `AUDIO_PROCESSOR=ffmpeg` the audio length is **not** adjusted to the target duration;
  the result says so (see "FFmpeg duration fitting" below).
- F0 allows 20 requests per minute for the whole resource, shared by all jobs: a 2,000-character
  chunk is one request, so a long transcript takes minutes in the `synthesizing` stage. Quota or
  rate errors fail the job with a clear message; nothing is retried automatically.
- Azure cuts a request at 10 minutes of audio without an error. Chunks are small (2,000
  characters by default) and a chunk within 10 s of the limit is rejected.
- The image grows with FFmpeg (Debian `ffmpeg`: about 405 MB -> 1.04 GB). A static FFmpeg build
  would be smaller but is an unsigned third-party binary, which was not chosen.
- Rotate the key in the Azure portal (Keys and Endpoint -> Regenerate) and update Render.

## FFmpeg duration fitting (Milestone 3C)

Implemented in a pull request; **not enabled in production** until the Product Owner has listened
to the result and accepted it. No new Azure resource, key or cost is involved: FFmpeg is already
in the image (3B) and runs on the instance.

**Check locally first** (no credentials): `cd backend && uv run python -m scripts.duration_smoke`
prints, for each case, the target, the natural source length, the processed PCM and the final MP3
(decoded, gapless header, ffprobe) and exits non-zero on any mismatch of more than one sample.
`--azure` is the live variant: it sends the public four-line sample transcript to Azure Speech once
per voice (2 requests, 259 characters each, F0 quota only) and writes before/after MP3s to
`backend/duration-samples/` to listen to; the key is read from `backend/.env` or the environment
and is never printed.

### Enable on Render

Render -> service **mydubb** -> **Environment** -> add `AUDIO_PROCESSOR=ffmpeg`; leave every other
variable as it is (`PROVIDER_MODE=mock` and `ALLOW_MOCK_PROVIDERS_IN_PRODUCTION=true` come from
`render.yaml`, which this milestone does not change; with all three components real they are no
longer needed but harmless). Save; Render redeploys the service. Then `/api/meta` reports
`providers: {translation: azure, speech: azure, audio: ffmpeg}`, `mock_mode: false` and
`provider_mode: azure` (the effective mode), the "mock" banner disappears, and a result shows
"Duration adjusted" with the target and measured durations. The service refuses to start if
`ffmpeg`/`ffprobe`, the `atempo` filter or the `libmp3lame` encoder is missing, never falling
back to the pass-through.

Optional cleanup after acceptance (a separate change, not part of this milestone): set
`PROVIDER_MODE=azure` and remove `ALLOW_MOCK_PROVIDERS_IN_PRODUCTION` in `render.yaml` and the
dashboard, so the service would refuse to start with any mock component.

### Roll back

Remove the `AUDIO_PROCESSOR` variable (or set it to `mock`) and save: audio processing returns to
the pass-through, exactly the configuration before 3C. If `PROVIDER_MODE` was changed to `azure`
for the cleanup above, set it back to `mock` and restore `ALLOW_MOCK_PROVIDERS_IN_PRODUCTION=true`,
otherwise the service refuses to start with a mock component. Code rollback follows the usual
rules below (this milestone has no database migration).

### Expected behavior and limits

- Processing time is a few seconds per minute of audio on a normal CPU and the job stays in the
  `processing` stage; Render Free has a small shared CPU, so allow longer for long audio. Each job
  uses temporary disk of about 4-10x the WAV size (24 kHz mono 16-bit is 2.9 MB per minute),
  removed when the job ends.
- A result that cannot be brought to the exact target fails the job (see the error codes in
  [API.md](API.md)); nothing is returned partially.
- The MP3 is exact for gapless-aware players (browsers, FFmpeg). A player that ignores the MP3
  header plays up to about 50-70 ms more; see [ARCHITECTURE.md](ARCHITECTURE.md#duration-fitting-milestone-3c).

## Operations

### Deploying

- Merge a pull request into `main`. CI runs on the merge commit; Render deploys it **only after
  the GitHub checks pass** (`autoDeployTrigger: checksPass`). Follow progress under the
  service's **Events**.
- Zero-downtime deploy: the new instance starts and receives traffic once `/api/health`
  responds; the old instance gets SIGTERM about a minute later, finishes running jobs for up to
  `JOB_SHUTDOWN_GRACE_SECONDS` (20 s), then exits within Render's default 30 s shutdown delay
  (`maxShutdownDelaySeconds` is not available on the Free plan).
  Jobs it could not finish are marked "interrupted" and must be resubmitted. Results produced
  by the old instance become "result expired".
- Changes to `render.yaml` on `main` are synced to the service by Render (Blueprint sync).
  Values marked `sync: false` or generated are not overwritten.

### Database migrations

- The container runs `alembic upgrade head` on every start, while the previous instance may
  still be serving. Migrations must therefore be **expand-only** (add nullable columns or new
  tables; rename/drop only in a later release after no code uses them).
- If the migration step fails, the container stops before the app starts and logs what to
  check. Migration errors are never ignored, and the database is never downgraded
  automatically.
- Never run `alembic downgrade` against production as part of a rollback.
- To see the production schema revision: Neon **SQL Editor** →
  `SELECT version_num FROM alembic_version;`

### Rolling back

Two kinds of compatibility matter:

| | Old code vs. newer **schema** | Old code vs. newer **Alembic revision** |
|---|---|---|
| Guaranteed by | Expand-only migrations | Nothing: an image only knows the migrations it contains |
| If broken | Old code may fail at runtime | Startup stops with `Can't locate revision identified by '<rev>'`; the rollback deploy fails and the database is unchanged; the current instance keeps serving because a zero-downtime deploy only switches traffic to an instance that started and passed its health check |

**Supported rollback targets**: deploys built from a commit whose
`backend/alembic/versions/` contains the database's current revision. Today the production
database is at `0002`, and every production deploy so far (from `3806012`, the merge of
PR #2, onwards) contains `0002`, so all of them are supported targets. After a future
migration (`0003`) is deployed, older deploys stop being supported targets.

**Before rolling back** (read-only checks):

1. Read the production revision: Neon SQL Editor → `SELECT version_num FROM alembic_version;`
2. Check the target commit (shown on Render's **Deploys** page):
   ```bash
   git fetch origin
   sh docker/rollback-target-check.sh <target-commit> <revision>
   ```
   `OK` means a supported target; `NOT SUPPORTED` means do not use Render's Rollback.

**Supported target: Render rollback**

1. Render → service → **Deploys** → the target deploy → **Rollback** → confirm. The rollback
   reuses the target deploy's build, environment variables and start command.
2. A dashboard rollback **disables auto-deploy**. After fixing the problem on `main` (via a
   pull request), re-enable auto-deploy in **Settings**.

**Unsupported target: roll forward instead (default)**

Revert the faulty change in a pull request (`git revert <commit>`), keeping every migration
file. The new image knows the current revision, so it starts normally; CI runs and Render
deploys it after the checks pass.

**Emergency only: run older code without its migration step.** Use only if rolling forward
is not possible in time, with the Product Owner's approval:

- Conditions: every migration between the target's newest revision and the database's
  revision is expand-only (read those migration files), and the target code was verified
  against the current schema (see "Rollback rehearsal").
- Render's **Rollback** cannot do this: it reuses the target deploy's environment variables.
  Instead: **Environment** → add `RUN_MIGRATIONS_ON_START=false` → save (Render redeploys the
  current commit without migrations; harmless because the database is already at its
  head), then **Deploys** → **Manual Deploy** → **Deploy a specific commit** → the target
  commit. Deploying a specific commit disables auto-deploy.
- Restore afterwards, in this order: merge the fix to `main` and wait for CI; delete
  `RUN_MIGRATIONS_ON_START` in **Environment** (it defaults to `true`); deploy the latest
  `main` commit; re-enable auto-deploy in **Settings**; confirm the logs show the migration
  step running again (no error) and run the production smoke test.

**Rollback rehearsal (test database only)** - verified on 2026-10-22 against a local
PostgreSQL database migrated to `0002` by the current image, with job data created by
the smoke test:

| Target image | Knows | Startup | Result |
|---|---|---|---|
| `18b4e40` (production) | `0001`, `0002` | default | Starts; smoke test passes |
| `002e2bb` (Milestone 2A) | `0001` | default | Exits: `Can't locate revision identified by '0002'`; database unchanged |
| `002e2bb` | `0001` | `RUN_MIGRATIONS_ON_START=false` | Starts; smoke test passes (schema compatible) |
| Current branch image | `0001`, `0002` | default, after the above | Starts; reads rows written by the `0001`-era code |

Repeat it for any pull request that adds a migration: build the previous production commit
and the new one (`git worktree add <dir> <commit>` + `docker build`), migrate a throwaway
database with the new image, then start the previous image against it with default
startup and with `RUN_MIGRATIONS_ON_START=false`, running `docker/smoke-test.sh` each time.
Never rehearse against production.

### Rotating secrets

- **Access Code**: service → **Environment** → `ACCESS_CODE` → set a new value (for example
  generate one with `openssl rand -base64 32`) → save; Render redeploys. Existing sessions stay
  valid until they expire. To sign everyone out immediately, run
  `DELETE FROM access_sessions;` in the Neon **SQL Editor**.
- **Database password**: Neon → **Roles** → reset the password → update `DATABASE_URL` in
  Render → save (redeploys).

### Troubleshooting

| Symptom | Likely cause |
|---|---|
| Deploy fails at startup with a settings error | Missing/invalid `DATABASE_URL`, or `ACCESS_CODE` shorter than 16 characters. The log names the variable (never its value). |
| `Can't locate revision identified by ...` followed by "database migration failed" | The deployed commit predates the database's migration (e.g. an unsupported rollback target). The database was not changed; see "Rolling back". |
| `alembic` connection error in the logs | Wrong Neon string (pooled `-pooler` host, missing `sslmode=require`, or reset password). |
| Site shows a Render error page after idling | Cold start of the free instance; wait and reload. |
| "Result expired" right after a deploy | Expected: results are kept on the instance's ephemeral disk. Generate again. |
| Custom domain stays unverified | DNS not propagated yet, leftover AAAA/forwarding records, or wrong CNAME target. |
| A commit on `main` is not deployed | Its CI failed (Render waits for checks), or auto-deploy was disabled by a rollback. |

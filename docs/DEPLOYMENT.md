# Deployment: online mock Private Beta (Milestone 2B)

Target: `https://mydubb.com` running the production Docker image with **mock providers**
(no Azure, no real translation or speech), on free tiers.

```
Browser ──HTTPS──► Render edge (TLS, mydubb.com) ──► Render Free web service "mydubb"
                                                     (Oregon, Docker image, 1 instance)
                                                          │
                                                          ▼
                                                   Neon Free PostgreSQL
                                                   (AWS US West 2, Oregon)
```

Neither Render nor Neon offers a California region; Oregon (US West) is the closest for both,
and keeping them in the same region minimizes database latency.

Configuration lives in [`render.yaml`](../render.yaml) (Render Blueprint). Secrets are never
stored in the repository or sent in chat:

| Variable | Source |
|---|---|
| `DATABASE_URL` | Neon direct connection string, pasted into Render once |
| `ACCESS_CODE` | Generated by Render (random 256-bit value); read it in the Render dashboard |
| Everything else | Fixed values in `render.yaml` |

## Free-tier behavior to expect

- **Render Free** web service: spins down after 15 minutes without traffic; the next visit
  waits for a cold start (often around a minute). 750 free instance hours per workspace per
  month. The filesystem is ephemeral: generated results disappear on restart, deploy or
  spin-down, and the app then reports "result expired".
- **Neon Free**: the database compute suspends when idle and wakes on the next connection
  (adds a short delay to the first request).
- If Render or Neon ever asks for a payment method or a plan upgrade during these steps, stop
  and check with the team; this setup must stay on free plans.

## One-time setup

### 1. Neon database

1. Sign in at https://console.neon.tech (signing in with GitHub is fine).
2. Create a project:
   - Project name: `mydubb`
   - Postgres version: **17** (same as CI)
   - Cloud provider: **AWS**, region: **US West 2 (Oregon)**
3. Open the project dashboard and click **Connect**. In the connection dialog:
   - Branch: `main` (or `production`, whichever is the default), database: the default
     (`neondb`), role: the default owner role.
   - Turn **Connection pooling OFF** so the hostname does **not** contain `-pooler`. Migrations
     run at startup and need a direct connection.
   - Copy the connection string. It looks like
     `postgresql://<role>:<password>@ep-<name>.us-west-2.aws.neon.tech/neondb?sslmode=require...`
4. Keep it only in your clipboard or password manager for the next step. Do not commit it or
   paste it into chat. The app normalizes `postgresql://` URLs itself; paste it unchanged.

### 2. Render Blueprint

1. Sign in at https://dashboard.render.com.
2. Click **New** → **Blueprint**.
3. Connect GitHub if Render asks:
   - Choose **GitHub**, authorize Render, and install the **Render** GitHub App.
   - On the installation page choose **Only select repositories** → `chutieu312/mydubb`
     → **Install**. (Render then sees only this repository.)
4. Back in Render, select the `chutieu312/mydubb` repository.
5. Blueprint name: `mydubb`; branch: `main`. Render reads `render.yaml` and lists one web
   service named `mydubb` on the **Free** plan in **Oregon**. Check both before continuing.
6. Render asks for the value of `DATABASE_URL`: paste the Neon connection string from step 1.
   `ACCESS_CODE` is generated automatically.
7. Click the button that creates the resources (for example **Deploy Blueprint**).
8. Open the `mydubb` service → **Events**/**Logs** and wait for the first deploy (the Docker
   build takes several minutes). A healthy start logs, in order:
   - `Running upgrade  -> 0001` and `Running upgrade 0001 -> 0002` (database migrations),
   - `Running in production with MOCK providers ...` (expected warning),
   - `Application startup complete.`
9. The service page shows its Render URL, e.g. `https://mydubb.onrender.com` (Render may add a
   suffix if the name is taken). Note the exact hostname; it is needed for DNS. Opening it
   should show MyDubb with the **Development mock mode** banner.
10. Get the Access Code: service → **Environment** → `ACCESS_CODE` → reveal and copy. Store it in
    your password manager. Log in on the Render URL to confirm it works.

### 3. Custom domain (GoDaddy DNS)

`render.yaml` already declares `mydubb.com`; Render adds `www.mydubb.com` automatically and
redirects it to `mydubb.com`.

1. In Render: service → **Settings** → **Custom Domains**. Both domains are listed as
   unverified, with the DNS records Render expects. If Render shows values different from
   the ones below, use Render's values.
2. In GoDaddy: **My Products** → `mydubb.com` → **DNS** (Manage DNS) → **DNS Records**:
   - **A** record, name `@`: edit the existing one (often "Parked") or add one, value
     **`216.24.57.1`**, TTL 600 seconds (or "1/2 hour"). Delete any other `A` records for `@`.
   - **CNAME** record, name `www`: edit the existing one (usually pointing to `@`), value
     **`<your-service>.onrender.com`** (the hostname from step 2.9), TTL 600 seconds.
   - Delete every **AAAA** record (Render uses IPv4 only; AAAA records break routing).
   - Under **Forwarding**, make sure no domain or subdomain forwarding is configured.
   - Leave `NS` and `SOA` records unchanged.
3. Check propagation (Windows Command Prompt, PowerShell or Git Bash):
   ```bash
   nslookup mydubb.com        # should answer 216.24.57.1
   nslookup www.mydubb.com    # should show the onrender.com hostname
   ```
   Propagation can take from minutes to a few hours.
4. In Render → **Custom Domains**, click **Verify** for each domain. Render then issues the TLS
   certificates automatically. Wait until both show as verified with certificates issued.

### 4. Online verification

1. Browser: open `https://mydubb.com` (desktop and phone). Check the padlock, the mock banner,
   log in, run one dubbing job, play and download the MP3, log out.
2. `http://mydubb.com` and `https://www.mydubb.com` must end up on `https://mydubb.com`.
3. Smoke test from Git Bash in the repository root (the Access Code is typed without echo and
   never stored):
   ```bash
   read -rs ACCESS_CODE && export ACCESS_CODE      # paste the code, press Enter
   echo ${#ACCESS_CODE}                             # prints only the length (Render: ~44)
   BASE_URL=https://mydubb.com SMOKE_SKIP_WRONG_CODE_CHECK=1 PYTHON=python sh docker/smoke-test.sh
   unset ACCESS_CODE
   ```
   Expected last line: `mock job <id> completed; result and audio retrievable`.
   `SMOKE_SKIP_WRONG_CODE_CHECK=1` avoids spending one of the 5 failed attempts per client per
   15 minutes allowed by the brute-force protection. A `login failed: HTTP 429` means that
   allowance is used up (all users behind the same IP share it): wait 15 minutes. `HTTP 401`
   means the pasted code is wrong or incomplete.
4. Security headers:
   ```bash
   curl -s -D - -o /dev/null https://mydubb.com/api/health | grep -iE "strict-transport|content-security|x-frame"
   ```
5. Client IP header check: in Render → **Logs**, search for `CLIENT_IP_HEADER`. No match after
   the logins above means the edge header is present and brute-force protection identifies
   clients correctly. If the warning
   `CLIENT_IP_HEADER 'cf-connecting-ip' is configured but absent` appears, report it: the
   per-client limit is then bypassable and needs a different header (the global limit still
   applies).

## Operations

### Deploying

- Merge a pull request into `main`. CI runs on the merge commit; Render deploys it **only after
  the GitHub checks pass** (`autoDeployTrigger: checksPass`). Follow progress under the
  service's **Events**.
- Zero-downtime deploy: the new instance starts and receives traffic once `/api/health`
  responds; the old instance gets SIGTERM about a minute later, finishes running jobs for up to
  `JOB_SHUTDOWN_GRACE_SECONDS` (20 s), then exits within Render's default 30 s shutdown delay
  (`maxShutdownDelaySeconds` is not available on the Free plan).
  Jobs it could not finish are marked "interrupted" and must be resubmitted. Results produced
  by the old instance become "result expired".
- Changes to `render.yaml` on `main` are synced to the service by Render (Blueprint sync).
  Values marked `sync: false` or generated are not overwritten.

### Database migrations

- The container runs `alembic upgrade head` on every start, while the previous instance may
  still be serving. Migrations must therefore be **expand-only** (add nullable columns or new
  tables; rename/drop only in a later release after no code uses them).
- Never run `alembic downgrade` against production as part of a rollback.

### Rolling back

1. Render → service → **Deploys** → pick the last good deploy → **Rollback** → confirm.
2. A dashboard rollback **disables auto-deploy**. After fixing the problem on `main` (via a
   pull request), re-enable auto-deploy in **Settings**.
3. Because migrations are expand-only, the older code runs against the newer schema; the
   database is not rolled back.

### Rotating secrets

- **Access Code**: service → **Environment** → `ACCESS_CODE` → set a new value (for example
  generate one with `openssl rand -base64 32`) → save; Render redeploys. Existing sessions stay
  valid until they expire. To sign everyone out immediately, run
  `DELETE FROM access_sessions;` in the Neon **SQL Editor**.
- **Database password**: Neon → **Roles** → reset the password → update `DATABASE_URL` in
  Render → save (redeploys).

### Troubleshooting

| Symptom | Likely cause |
|---|---|
| Deploy fails at startup with a settings error | Missing/invalid `DATABASE_URL`, or `ACCESS_CODE` shorter than 16 characters. The log names the variable (never its value). |
| `alembic` connection error in the logs | Wrong Neon string (pooled `-pooler` host, missing `sslmode=require`, or reset password). |
| Site shows a Render error page after idling | Cold start of the free instance; wait and reload. |
| "Result expired" right after a deploy | Expected: results are kept on the instance's ephemeral disk. Generate again. |
| Custom domain stays unverified | DNS not propagated yet, leftover AAAA/forwarding records, or wrong CNAME target. |
| A commit on `main` is not deployed | Its CI failed (Render waits for checks), or auto-deploy was disabled by a rollback. |
